# 并发压测：v1.1 决策证据（keep-alive / 热键预热）

- **日期**：2026-08-14
- **环境**：macOS（Apple Silicon），loopback，三节点自管理集群（18401-3），
  每节点 8 worker / pool_size=4（SQLite WAL）
- **负载**：Python SDK（8 线程共享一个 ClusterClient）随机热点键 select
- **脚本**：`scripts/loadtest_sdk.py`（bench：cache on/off 对照；storm：
  负载中杀 node-c → 复活，misses 时间线采样）

## 1. 稳态对照（8000 请求 / 100 热点键 / 8 并发）

| 配置 | 吞吐 | p50 | p95 | p99 | 命中率 | DB 回源读 |
|---|---|---|---|---|---|---|
| cache on | **817 req/s** | 7.17ms | 22.32ms | 46.92ms | 100%（8000 hits / 0 miss） | **0** |
| cache off | 787 req/s | 7.44ms | 23.33ms | 48.89ms | — | 8000（全回库） |

并发梯度（cache on）：

| workers | 吞吐 | p50 | p99 |
|---|---|---|---|
| 1 | 228 req/s | 4.14ms | 15.91ms |
| 4 | 594 req/s | 5.52ms | 21.94ms |
| 8 | 817 req/s | 7.17ms | 46.92ms |

稳态 redirects = 0（SDK 直连 owner，两端环一致）。

## 2. 关键结论

### ① 客户端连接开销是当前主要成本（keep-alive 的证据）

服务端处理延迟在期1基线为 p99 ≈ 0.4ms（含 DB 读），缓存命中更低。
而单线程下客户端 p50 = 4.14ms —— **每请求约 3.8ms 是客户端开销**
（每请求新建/关闭 TCP + Python 编解码），且随并发上升恶化（GIL/争用）。
吞吐 1→4→8 线程亚线性增长（228→594→817），延迟同步变差，
800 req/s 是 **Python 客户端侧天花板**，非服务端能力上限。

**但**：服务端 HTTP 模型为 Connection: close（一期一响应一关连接），
keep-alive 必须服务端 + SDK 联合改造（见 README §9「暂不引入」）。
数据支持"做 keep-alive 客户端延迟会大幅下降"，**是否做取决于是否愿意
重启 HTTP 模型演进项** —— 压测本身不构成必须立刻做的理由。

### ② 缓存在并发下的收益形态

cache on/off 端到端只差 ~4%（817 vs 787 req/s）—— 因为①中的客户端开销
淹没了服务端省下的 DB 读。缓存的真实收益体现在**服务端**：
DB 回源读从 8000 次降为 0（降 100%），节点 CPU/IO 余量与慢后端场景下的
尾延迟才是受益面。loopback + 单行 SQLite 读（µs 级）是缓存收益的
最不利观测环境；真实部署（网络 RTT + 更慢的 DB）收益会更显著。

### ③ 归队 miss 风暴：未观测到（热键预热继续不做）

storm 模式（cache ttl/blacklist 同取 2s——I1 约束下无法同时长 TTL + 短黑名单）：

- t=12s 杀 node-c、t=18s 复活；misses 时间线每 0.5s 增量稳定在
  ~20-70，**复活后无尖峰**（18.4s 起 Δ=33/39/23，与前后窗口无差异）。
- 机理上风暴已被现有机制封住：**I1 保证归队时旧条目必然已过期**
  （blacklist ≥ cache_ttl），不存在"带着旧缓存归队"；冷缓存由流量在
  ≤1 个 TTL 内自然重建，同键并发 miss 被 Singleflight 合并成一次回源
  （本次 100 热键、~800 req/s 下重建瞬时完成）。
- 故障窗口内的 1612 次"失败"是断言 row_count==1 不成立：owner 不可达
  期间其归属键经替补就地处理，替补库没有该行（**spec §5.1 例外②的
  已记录语义**，非缺陷），窗口占比与实际失败率（7%）吻合。

**结论：热键账本 + 预热的判据（归队 miss 率/DB QPS 尖峰）依旧不成立，
维持 spec "v2，看指标" 的搁置决定。**

## 3. 决策落点

| v1.1 项 | 压测前状态 | 压测后结论 |
|---|---|---|
| SDK keep-alive | 搁置（零依赖/服务端不支持） | **数据证实客户端开销主导**；但需服务端 HTTP 模型配合，仍属"愿不愿意重启架构演进项"的决策，压测不构成强制理由 |
| 热键预热 | 搁置（无风暴证据） | **继续搁置**：实测无风暴，I1 + Singleflight + TTL 已封住机理 |
