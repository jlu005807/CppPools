# CppPools 分布式集群与行级缓存设计

> 状态：**v2（已经评审修订）**，可据此开工
> 前置：DB 中间件改造已完成（多数据源路由 + 通用 CRUD + SQLite 后端，见
> `2026-08-06-db-middleware-design.md`，本文简称「既有 spec」）
> 修订依据：见 §13 评审修订记录

## 1. 定位与目标

把现有 CppPools 单节点中间件作为**完全无状态的接入节点**，组成一个分布式系统：

- 客户端用**一致性哈希环**把每一行数据的归属路由到唯一 owner 节点；
- owner 节点提供**本地行级缓存**，读命中不回数据库；
- 数据库始终是真理之源，节点缓存是**滞后 ≤ TTL** 的可丢弃副本。

设计思路借鉴 Alluxio Dora（客户端建环、归属路由、failover 黑名单、可再生哲学），
但**不追求与 Dora 字节兼容**（见 §3.1 注）。

### 1.1 为什么这个底座更简单（三个结构性红利）

| 红利 | 来源 | 消解的问题 |
|---|---|---|
| **节点无状态** | 数据全在 DB，节点只是"连接+校验+缓存" | 扩缩容 = 改环，无数据迁移（Dora 的 Cache Rebalance 难题不存在）；节点可随时杀/换 |
| **唯一键单行操作** | 既有决策：where 必须 PK/UNIQUE | 每操作恰好一个缓存键（无范围失效）、天然幂等（重试安全）、单分片（无分布式事务） |
| **校验与执行分离** | Database NVI 基类 | 缓存是 `do_*` 层的装饰，安全管道全程不动 |

### 1.2 非目标与适用前提（本版不做 / 不保证）

| 项 | 说明 |
|---|---|
| **跨行/跨表事务** | 接口仍是单行操作，无事务语义 |
| **对外部写入者的可见性** | **本设计假设目标表仅由本集群写入**。若 DB 被 CLI/报表/其他应用直接修改，节点缓存无从感知，旧读窗口 ≤ TTL 且按键不可预测。逃生舱见 §6.1 的 `cache.tables` 白名单 |
| **副本与高可用存储** | 缓存不是副本、是加速器；DB 自身高可用不在范围 |
| **节点间通信** | 节点之间**不通信**（无心跳、无缓存互查、无失效广播）——这是"无协调"基调的硬边界 |
| **动态成员管理** | 成员是静态配置，改配置 + 滚动重启（§5.4） |
| **鉴权 / 多租户 / 传输加密** | 假设**可信网络 + 可信客户端**，集群端口不对公网暴露；控制类请求头（§3.6）无鉴权 |
| **负缓存** | 不缓存"不存在"的结果（扩展位 §10） |
| **缓存持久化 / 落盘预热** | 缓存纯内存，进程重启即空 |
| **schema 热变更** | 继承既有 spec：schema 变更需重启服务。重启即清缓存，故"旧列集整行"不会被留下 |
| **请求级一致性覆盖** | 不提供 `"consistency":"strong"` 之类的按请求绕缓存开关 |
| **多列 where / 范围查询** | 与中间件本体一致，刻意收窄 |

继承既有 spec §16 的已知限制（无事务、连接不自动重连、请求行/请求体上界等），本文不复述。

## 2. 架构全景

```
SDK 客户端（本地建环）
│  ① 拉拓扑：GET /api/v1/cluster（任意节点，lazy 刷新 30s）
│  ② 归属判定：ring(datasource, table, 键列, 键值, attempt) → owner
│  ③ 点对点直连 owner（哈希参数由服务端下发，两端同参）
▼
┌──────────── CppPools 节点 × N（无状态，可随时替换）──────────┐
│  HTTP 接入 → 三大池子 → NVI 校验管道（白名单/唯一键/严格类型） │
│       → CachingDatabase 装饰器（行级缓存，写穿透）             │
│            → SqliteDatabase / MysqlDatabase（后端不感知缓存）  │
│  每数据源一份共享 RowCache（§4.1.1）                          │
└─────────────────────────────────────────────────────────────┘
▼
数据库（真理之源；所有节点连同一组数据源，§6.3 校验一致性）
```

**两层路由正交**：

```
客户端: (datasource, table, 键列, 键值) ──环──> owner 节点
节点内:  table ──registry──> datasource（既有逻辑，不变）
```

环决定"哪个节点缓存并处理这一行"，registry 决定"数据在哪个库"。
所有节点的数据源配置必须完全相同（约束的强制手段见 §6.3）。

## 3. 路由层：单 owner 模型

### 3.1 哈希与环（规范性）

> **注（事实性更正）**：本节参数**不与 Alluxio Dora 字节兼容**。实测核对：
> Dora 的 vnode 哈希输入是 `WorkerIdentity`（UUID 16B 大端 + LE32 version）而非
> node_id 字符串；Dora 默认 vnode 数是 **5**（100 是它的 maxAttempts）；
> Dora 的 attempt 从 **1** 起；Dora 全链路用 **signed** int32。
> 本设计自行选参，**正确性只依赖"客户端与服务端同参 + §3.2 黄金向量"**，
> 不依赖与 Dora 一致。禁止为"更贴近 Alluxio"而单端改参。

| 项 | 规范 |
|---|---|
| 哈希函数 | murmur3 32-bit，**seed = 0** |
| 哈希输出 | **无符号 32 位**（Python：`mmh3.hash(data, 0, signed=False)`；C++：`uint32_t`） |
| 字符串编码 | 一律 **UTF-8**（含 node_id、datasource、table、列名、键值） |
| `LE32(x)` | 小端无符号 4 字节 |
| vnode 数 | 每节点 **100**（自选：小集群下 5 个 vnode 分布过于不均） |
| vnode 哈希输入 | `LP(node_id) ‖ LE32(vnode_index)`，`vnode_index ∈ [0, 100)` |
| 查询哈希输入 | `LP(datasource) ‖ LP(table) ‖ LP(列名) ‖ LP(键值串) ‖ LE32(attempt)` |
| `LP(s)` | 长度前缀编码：`LE32(len(utf8(s))) ‖ utf8(s)`（**禁止用分隔符拼接** —— 值可含任意字符，`"a/b"+"c"` 与 `"a"+"b/c"` 会撞键） |
| attempt 起点 | **0** |
| 环容器 | 按哈希值升序（无符号比较）；查询取**顺时针第一个**，越界回绕到首元素 |
| vnode 冲突 | 同一哈希值出现多个 vnode 时，按 `(node_id, vnode_index)` 字典序做**确定性 tie-break**，不允许后者覆盖前者（覆盖会让环依赖插入顺序） |
| 空环 | 配置校验保证至少一个节点（§6.1），空环不可达；单节点时任何键都归它 |

**键值串化规则**：整数用十进制、无前导零、负号 `-`、无 `+`；字符串原样（UTF-8）。
REAL 键列的请求不参与环路由（见 §5.5）。

### 3.3 路由键与缓存键：同一个 4 元组

**路由键 = 缓存键 = `(datasource, table, 唯一键列名, 键值)`。**

- **必须含 datasource**：既有 spec §4.1 允许同名表跨数据源共存（分片场景），
  显式 `datasource` 字段优先级最高。若键缺此维度，`shard0.orders#42` 与
  `shard1.orders#42` 会撞同一缓存键 ⇒ **静默返回另一个库的行**（正是既有
  spec §4.1 极力杜绝的静默数据错乱，只是从写侧换到读侧）。
- 请求未显式指定 datasource 时，**两端一律用空串占位参与哈希**（期2 修订，
  取代 v2 初稿"服务端用实际解析值"的写法）：LP("main")≠LP("")，若客户端
  用空串而服务端用实际值，两端哈希输入不同即可能选出不同 owner —— 客户端
  可见口径（显式值或空串）是唯一可证明两端同键的编码。表名唯一时全集群
  解析结果相同，空串占位不影响归属正确性。**缓存键（RowCacheKey）仍用
  服务端解析的实际值**：那是节点内命名空间，与路由编码解耦。
- **多唯一键的确定性规则**：一次 insert 可能同时给出多个唯一列（如 PK `id` 与
  UNIQUE `tag`）。规则：**取 schema 列序中第一个出现的唯一列**。客户端与
  服务端共用此规则，并写入 conformance 断言。
- 类型不会撞键：既有严格类型校验保证同一 `(table, 列)` 的 where 值类型唯一
  （整数 `42` 与字符串 `"42"` 不可能出现在同一列上）。唯一例外 REAL 列见 §5.5。
- **实现约束**：缓存键在代码里是**结构化元组**（逐字段比较），
  **禁止**以拼接字符串实现；哈希输入才序列化为字节（§3.1 的 `LP`）。

### 3.4 单 owner：一致性问题的结构性消解（三步论证）

```
① 同一 4 元组的所有操作路由到同一 owner 节点（§3.3 + 环）
② 该节点内该键只有【一份】缓存条目（§4.1.1：RowCache 每数据源共享）
③ ⇒ 该条目只有一个写入者 ⇒ 无需失效广播、无需分布式锁
```

**三步缺任何一步契约都不成立。** 特别是 ②：若缓存是 per-connection 的，
①仍成立而②失效 —— 写走连接 1、读走连接 2 就会读到旧值（评审 B1）。

已知裂缝（均已封堵或明确纳入契约）：

| 裂缝 | 封堵 |
|---|---|
| 归属切换瞬间（故障切换/拓扑变更） | §5.2 三条规则 + §5.4 epoch 门控 |
| 同一行的多唯一键访问路径 | 两个独立条目、可能不同 owner；写只失效 where 携带的键，另一键由 TTL 封顶（§4.2） |
| 读回填遮蔽已成功的写 | §4.3.1 世代号 CAS 回填 |
| owner 健康但被部分客户端绕过（灰度故障） | 仅 TTL 封顶；纳入契约例外（§5.1） |

### 3.5 attempt 绕行

客户端对 owner 请求失败（连接失败/超时）时：

1. 该节点加入本地黑名单（TTL 60s，§7）；
2. `attempt += 1` 重查环，落到环上另一存活节点（替补）；
3. 替补按 §3.6 决策矩阵**就地处理但不缓存**。

attempt 上限与全黑名单降级见 §7。

### 3.6 非 owner 收到请求：307 重定向 + 归属决策矩阵

**服务端权威自判**：节点对每个 CRUD 请求计算 `is_owner = (ring.owner(key) == self.node_id)`
—— 它持有集群配置与环，**不依赖客户端申报**（评审 B3：依赖客户端头是安全闸门的
结构性倒退，与项目"NVI 强制校验"哲学相悖；curl 与旧版 SDK 不带头就会误缓存）。

**非 owner 且客户端未声明绕行 ⇒ 返回 `307 Temporary Redirect` + `Location: <owner>/…`**
（307 保留 POST 方法与 body）。**不做代理转发**——否决理由：代理需要一个仓库里
不存在的出向 HTTP 客户端（≈280 行），且转发在阻塞模型下占住 worker 线程，
owner 变慢会打满本节点线程池造成级联故障（评审 W8/P0-2）。307 零新增依赖、
零线程占用、天然无环路，且精确覆盖非直连场景的三个用途（curl 调试、SDK 灰度、
视图不一致窗口）。curl 需加 `-L`。

**决策矩阵（规范性）**：

| is_owner | `X-CppPools-Fallback` | epoch 匹配 | 行为 | 缓存读/回填 | 失效 |
|---|---|---|---|---|---|
| 是 | — | 是 | 本地处理 | **允许** | 必须 |
| 是 | 有 | 是 | 本地处理 | **允许**（提示只能让节点更保守，不能更激进） | 必须 |
| 是 | — | **否** | 本地处理 + 回 `X-CppPools-Epoch` | 禁止（§5.4） | 必须 |
| 否 | 无 | — | **307 → owner** | 禁止 | 不涉及（未执行） |
| 否 | **有** | — | **就地处理**（客户端已判定 owner 不可达，不再重定向） | 禁止 | 必须 |

**提示单调性原则**：客户端请求头只能让节点**更保守**（不缓存、不重定向），
永不能让节点**更激进**（去缓存、去信任）。这条原则一次性防住整类请求头缺陷。

**无键请求不参与环路由（期2 补充）**：两类请求无法在执行前确定路由键，
直接本地处理（不做归属检查，缓存语义不变）：① insert 未给出任何唯一列的
非 NULL 值（纯自增，键落库前未知；insert 本不缓存行，§4.3.2）；② where 列
为 REAL 型（决策⑫：浮点键不参与环路由）。有键 insert 的路由键取 **schema
列序中第一个"给了值且非 NULL"的唯一列**（与上文多唯一键规则同源）。

## 4. 缓存层：行级缓存 + 写穿透

### 4.1 形态与位置

- **节点本地内存缓存**（进程内）。Redis 共享缓存模式是扩展位（§10）。
- `CachingDatabase : Database` **装饰器**，包在真实后端外：

```
校验管道（基类 public 方法，不变）
    → CachingDatabase::do_select / do_insert / do_update / do_remove
        → 缓存逻辑 + 委托内层 public 方法
            → SqliteDatabase（不变，不感知缓存）
```

#### 4.1.1 缓存实例的共享粒度（规范性）

> **`RowCache` 是「每数据源一个共享实例」**（`std::shared_ptr<RowCache>`，
> 由 `DataSourceRegistry::build()` 创建，注入该源**全部槽位**的
> `CachingDatabase`）。**不是 per-connection。**

- 强制理由（评审 B1/P0-1，双重代码证据）：`ConnectionFactory` 按 `pool_size`
  **逐槽调用**、且探活失败会**重建时再调**。若缓存是装饰器自有成员：
  命中率 ÷N、写失效只清 1/N 份（§5.1 契约在单节点内即为假）、
  探活重建让缓存归零、内存 N×、**指标无处可取**（池不暴露元素）。
- `RowCache` **内部自持锁**：建议 16 分片（按键 hash 取模），避免
  `pool_size` 条连接争同一把锁。
- `Entry`（registry 内部）新增 `std::shared_ptr<RowCache> cache` 字段，
  供指标读取与 §5.2 规则 B 清缓存使用。
- **probe 实例不装饰**：registry 建池前用于自省表清单的临时实例随即销毁，
  装饰它只会白建一份缓存。
- 需同步修订 `database.h` 的线程模型注释（"单实例被一条连接独占"）：
  装饰器是该注释的第一个例外——它跨连接共享状态。

#### 4.1.2 已知限制：命中仍需借连接（评审 W3）

装饰器包在池化元素上 ⇒ **必须先借到连接才能问缓存**。后果：

- 并发读上限仍是 `pool_size`；池打满时一个本可零成本命中的读**仍返回 503**；
- §4.4 Singleflight 的合并面被限制在"持有连接的请求"之间。

**本版接受此限制**（方案 C），理由：期 1 的目标是钉死缓存一致性语义；
把缓存前置到池外（方案 A）需要**把校验管道从 Database 实例提升到数据源级**
（当前校验用的是每连接自省的 `schema_` 成员），那是动核心安全代码的重构，
应有独立评审周期。缓解手段：`pool_size` 可调大（WAL 下多读者并发安全）。

**升级触发条件**（写入 §11 期 1 验收）：若压测显示命中路径因 `pool_size`
成为瓶颈（`cache_hit` 高但 `pool_acquire_failed_total` 同时高），则把方案 A
排入 v1.1，届时必须同时解决"命中路径仍须跑校验管道"（否则非法列名在
缓存路径变成 200 少一列，违反 §9 的语义等价断言）。

### 4.2 缓存键与条目

| 项 | 内容 |
|---|---|
| 键 | `(datasource, table, 唯一键列名, 键值)`（§3.3） |
| 值 | **整行数据**（全列，列名→Value）+ **快照时刻** |
| 快照时刻 | = **发起 DB 读的时刻**（非回填完成时刻；否则实际旧读窗口是 `TTL + DB 读延迟`，上界失守） |
| 时钟 | **`steady_clock`**（单调；`system_clock` 遇 NTP 回拨会致条目永不过期）。TTL 是节点本地时长，**集群无对时要求** |
| TTL | 默认 60s，过期条目**读时惰性重取**（无后台清理线程，与项目既有风格一致） |
| 容量 | **双阈值**：`max_entries`（默认 10 万）+ `max_bytes`（默认 256MB），任一超限即 LRU 淘汰 |
| 单条上限 | `max_entry_bytes`（默认 64KB）：超限不缓存，计 `cache_bypass_total{reason="too_large"}`。理由：TEXT 列无长度上限，10 万 × 100KB = 10GB（项目对其他池一律有界，缓存不该是唯一无界维度） |
| 只缓存什么 | **仅 `kOk` 且 rows 非空的单行结果**。`kBackendError`（含"脏数据"错误）、`kInvalidRequest`、空结果集（负缓存）一律不缓存 |

**投影必须复现的三条可观测语义**（conformance 已钉住，装饰器自算投影时逐条复现）：

1. 投影顺序 = **请求顺序**（非 schema 顺序）；
2. 重复列名**不去重**（请求 `["age","age"]` 必返回两列）；
3. 空结果集**仍带全部列名**。

实现要点：装饰器把 `req.columns` 清空后委托内层取整行（后端在 `do_select`
末尾自己做投影），再按上述语义自算投影。

**不做跨键关联**：`(main,users,id,42)` 与 `(main,users,tag,"a-1")` 是两个独立
条目（可能归属不同节点），写只失效 where 携带的键。否决理由：跨键关联需要
"值→键"反查索引且跨节点失效需要通信，与"无协调"基调冲突；多唯一键交叉访问
同一行是少数场景，TTL 60s 的旧读窗口在契约内。

### 4.3 写语义：write-through + 写后失效

写请求**同步直达 DB**，DB 确认成功后才返回客户端；缓存只做减法（删键），
不做加法（不写入中间件自己算出的值）。

```
insert/update/delete:
  1. 失效对应缓存键（前置删除）
  2. 委托内层落库（真理之源先行，同步等待）
  3. 再次失效对应缓存键（后置删除，覆盖步骤 1-2 间的回填）
  4. 返回后端结果
select:
  1. 查缓存 → 命中且未过期 → 投影返回（不回库）
  2. miss → 记录世代号 → 委托内层查库 → CAS 回填（§4.3.1）→ 返回
```

**双删而非单删**：借鉴 Dora 的"先失效后写元数据"（崩溃时落在安全侧）。
若只有后置删除，"SQL 成功 → 删键前抛异常"会留下脏条目到 TTL。

**失效而非更新**的理由：update 的读改写结果、insert 的自增主键都在后端才
最终确定；并发写时"更新缓存"的完成顺序可能与 DB 落库顺序相反（缓存与 DB
终态不一致且无人察觉）；DB 还可能有外部写入者。删除让缓存永远只存
"从 DB 读出来的数据"，一致性不需要任何额外协调。

**写-写并发是安全的**（已论证，无需额外机制）：每个写都在提交后无条件删键，
最后一次删除必然发生在所有提交之后 ⇒ 终态必为空 ⇒ 下次读回源拿最新值。

#### 4.3.1 回填的失效感知（规范性，评审 B2）

**无故障稳态下**的读-写交错会遮蔽已成功的写：

```
读 R: miss → DB 查询取到快照 v0
写 W: 落库 v1 → 删键（此刻无条目，删除是 no-op）
读 R: 回填 v0                      ← 已返回 200 的写，60s 内读不到
```

Singleflight 会把窗口从"一个读者"放大到"所有等待者"（leader 回填 v0 并分发
给全部 waiter）—— 两个特性叠加放大彼此危害。

**机制**：RowCache 每分片维护单调递增 `seq`（失效即 `++seq`）。

- 读 miss：进入回源前记录 `seq0 = shard_seq(key)`；
- DB 返回后：**仅当 `shard_seq(key) == seq0` 时才回填**，否则丢弃结果、
  直接返回（不缓存）；
- Singleflight 的 in-flight 结果同样受此检查约束：失效发生后，等待者拿到的
  结果**只用于返回、不入缓存**。

分片级（而非全局）世代号：把"任意键的失效作废所有并发回填"的浪费面缩小 16 倍。

#### 4.3.2 失效口径（规范性）

| 场景 | 失效动作 |
|---|---|
| insert 带显式唯一键 | 失效该键（按 §3.3 确定性规则选列） |
| 自增 insert（无显式唯一键） | no-op（新行不可能有旧条目；无负缓存） |
| update / delete | 失效 where 携带的那一个键 |
| 未改变 DB 的返回（insert 409、update/delete affected_rows=0） | 不失效 |
| delete 后同键重建 / update 改动唯一键列本身 | 另一唯一键的旧条目残留，由 TTL 封顶（§3.4 裂缝 2） |

> **不变量 I0：失效永不 bypass。**
> 任何**已改变 DB** 的操作必须无条件失效对应缓存键 —— 无论归属门控、
> 请求头、epoch 不匹配、REAL 键列、容量上限、`cache.enabled` 曾如何取值。
> bypass 只关闭两个动作：**读命中**与**回填**。
>
> 反例（本不变量要防的）：owner 收到带 `Fallback` 头的写 → 若 bypass 连
> 失效一起跳过 ⇒ **owner 亲手落库、亲手留下自己的脏条目**（评审 B5）。

装饰器语义因此定义为三个独立开关：`read_hit` / `backfill` / `invalidate`，
其中 **`invalidate` 恒为 on**。

### 4.4 击穿防护：Singleflight

同键并发 miss 合并为一次回源（`unordered_map<Key, shared_future<Row>>` + 分片锁）。
覆盖热点行、冷启动、TTL 集中过期、归队风暴。受 §4.3.1 世代号约束。

### 4.5 回填并发上限（重新定位）

> 评审 W3 指出：在方案 C 下能进入 `Database::select` 的请求已持有连接，
> 故同时回源数**恒 ≤ pool_size**，"阈值 = 连接池大小"的信号量**永不触发**；
> 连接池本身就是那个 bulkhead（`acquire_timeout → 503` 已提供不排队死等）。

**本版不实现独立的回填信号量。** 保护 DB 的职责由 `pool_size` 承担；
`cache_bypass_total{reason="overflow"}` 相应移除。若将来采用方案 A
（缓存前置到池外），此机制需重新引入并给出与池无关的独立阈值。

### 4.6 装饰器的实现约束

| 约束 | 说明 |
|---|---|
| **双重校验** | `do_*` 是 protected 且无 friend，装饰器写不出 `inner_->do_select()`，只能调 public `inner_->select()` ⇒ 校验管道跑两遍。正确性无损（校验幂等），代价是每次一次额外 schema 线性查找。**本版接受**（不加 friend、不改 `do_*` 可见性），在 §8 的延迟指标里可见其成本 |
| **schema 提供** | 装饰器构造为 `Database(inner->schema(), inner->name())`，拷一份内层 schema（`Schema` 是纯值类型，仅建连时一次深拷贝） |
| **委托** | `healthy()` / `backend_type()` 机械委托内层 |
| **写放大（已知成本）** | `SqliteDatabase::do_update` 内部调**自身** `do_select` 做读改写，装饰器在外层不可见 ⇒ **每次 update 至少一次 DB 读，即使整行就在缓存里**；且这次读到的最新整行被内层用完即弃（装饰器只能删键）⇒ 下次读又一次 DB 读。**缓存收益集中在读路径**，写多的负载可能整体变慢。优化方案（后端回吐更新后整行）列入 §10 |

## 5. 故障处理

### 5.1 一致性契约（对外承诺）

**稳态定义**：所有客户端的拓扑视图一致（同一 epoch）**且**无客户端将该键的
owner 列入黑名单。

> **稳态同键强一致**：经同一唯一键的写后读立即可见（由 §3.4 三步论证 +
> §4.1.1 共享粒度 + §4.3.1 回填失效感知**共同**保证 —— 单靠"写穿透"这个词
> 不充分）。
>
> **最终一致，旧读窗口 ≤ TTL（60s）** 的四种情形：
> ① 经**另一唯一键**读同一行；② **故障切换期**（客户端绕行中）；
> ③ **拓扑变更期**（epoch 未收敛）；④ **外部写入者**修改了 DB（§1.2）。

### 5.2 三条规则与两条不变量

| 规则 | 内容 | 封死的裂缝 |
|---|---|---|
| **A. 归属门控** | 非 owner（服务端自判，§3.6）处理请求时：读直接查库、写直接落库，**不读不填缓存**（失效照做，I0） | 孤儿脏条目：替补缓存了数据，owner 归队后路由不再经过它，无人失效 |
| **B. 归队清缓存**（best-effort 优化，非正确性依赖） | 节点收到 `X-CppPools-Rejoin: 1` 时清空本地缓存（幂等，10s 内至多一次） | 加速收敛，避免归队瞬间供应"刚要过期"的条目 |
| **C. TTL** | 所有条目 TTL 60s | 一切残余窗口（正确性的真正承担者） |

> **不变量 I1：`blacklist_ttl ≥ cache_ttl`。**
> 满足时"黑名单期间错过的写被旧缓存遮蔽"这一裂缝**由 TTL 单独封死**：
> 客户端拉黑 owner 后至少 `blacklist_ttl` 不回切，期间 owner 的所有旧条目
> （缓存于拉黑之前）最迟在 `cached_at + cache_ttl` 过期 ⇒ 回切时凡"错过写"
> 的条目均已过期。
> **强制手段**：两个 TTL 由服务端经 `/api/v1/cluster` 一并下发（§6.2），
> 启动时校验 I1，不满足则 fail-fast。

规则 B 因此**降级为性能优化**（评审 W2）。它本身不可靠：客户端进程重启会
丢黑名单状态、多客户端互不相识、curl 永不发送、节流可能吞掉——但这些都不再
危及正确性。**不引入任何归队检测机制**（否决节点自检心跳/邻居探测：需要节点
间通信，与 §1.2 硬边界冲突）。

### 5.3 故障时间线

```
t0   owner A 稳态：读写经 A，缓存加速，写穿透                → 同键强一致
t1   A 故障：SDK 超时 → A 进黑名单（≥ cache_ttl，I1）
t2   attempt+1 → 替补 B：带 Fallback 头就地处理，不缓存（规则 A）→ 正确，无加速
t3a  A 崩溃重启：内存缓存已消失 → 自然冷启动                 → 安全
t3b  A 抖动恢复（缓存还在）：I1 保证旧条目已过期；Rejoin 头加速清空 → 安全
t2'  【灰度故障】A 一直健康，只是被客户端 X 判定不可达：
     X 经替补写 v1 → A 手里 v0 继续服务客户端 C
     规则 A/B 均不生效，仅 TTL 封顶 → 已纳入 §5.1 例外 ②
t4   TTL 封顶一切残余（≤60s）
```

**可选强化（v1.1）**：替补在能连通 owner 时优先 **307 重定向回 owner**
（而非就地处理）—— 写经 owner 执行则 owner 自己失效自己的缓存，单写入者
前提保住，灰度故障脏读窗口从 60s 降到 0。代价：客户端多一跳。
本版不做（客户端已判定 owner 不可达，重定向大概率再失败一次）。

### 5.4 拓扑变更：epoch 门控

滚动重启期间必然出现**双自认 owner**：节点 A 已重启（新环，认为 owns K）、
节点 B 未重启（旧环，也认为 owns K），客户端视图因 30s lazy 刷新而参差 ⇒
两者都通过服务端自判门控 ⇒ 都缓存、都写 ⇒ §3.4 论证整体失效。
窗口可达数分钟（N 节点滚动 + 30s 刷新滞后）。

**机制（规范性）**：

- 客户端每请求携带 `X-CppPools-Epoch: <建环所用 epoch>`；
- 节点比对 `self.epoch`：**不相等 ⇒ 该请求 bypass 读命中与回填**
  （失效照做，I0），响应头回 `X-CppPools-Epoch: <self>`；
- 客户端见 epoch 不匹配**立即刷新拓扑**（不等 30s）。

效果：任一端视图落后即自动退化为"正确但无加速"，双写入者不可能同时缓存
—— 与规则 A 同构的保守化。

**运维流程**：递增 `epoch` → 逐节点重启（重启即空缓存）→ 客户端 ≤30s 收敛。
零脏读窗口的做法：变更前临时调小 `ttl_ms`。
`§6.1` 的"改配置 + 滚动重启（无状态，安全）"仅指**数据**安全；缓存侧的归属
漂移由本节负责。

### 5.5 重试语义与幂等矩阵

| 操作 | 幂等性 | SDK 自动重试 |
|---|---|---|
| select | 幂等 | 是（503/超时退避重试，含 attempt 绕行） |
| update / delete（唯一键定位） | 幂等 | 是 |
| insert **带显式唯一键** | 重试撞 409 = 已生效 | 是（409 交调用方判定） |
| insert **自增主键** | **非幂等**（可能插两行） | **否**，失败上抛调用方 |

400 永不重试；409 不重试、交调用方；**307 由客户端跟随**（不计入重试次数）。

**REAL 键列的处理（判据在列、不在值，评审 W11）**：既有严格类型校验允许
**整数值赋给 REAL 列**，于是 `42` 与 `42.0` 会串化成不同键、路由到不同 owner
（同一行两个 owner，§3.4 前提失效）。规范：

- 若 where 列的 `ColumnInfo::kind == kReal`：该列的所有请求
  **不参与环路由**（SDK 任选存活节点）且 **bypass 读命中与回填**；
- **失效照做**（I0）；
- 判据是列的静态类型（两端都能从 schema 一致判定），不是客户端传的值形态。

### 5.6 归队 / 冷启动 miss 风暴治理

| 优先级 | 手段 | 阶段 |
|---|---|---|
| 1 | Singleflight（§4.4） | 期 1 |
| 2 | 连接池天然限流（§4.5：pool_size 即 bulkhead） | 已有 |
| 3 | **热键账本 + 后台预热**：清缓存时保留"哪些键热"的账本（键名 LRU 1 万条），归队后后台限速回源重建 | v2，看指标 |
| 备选 | 慢启动归队（路由权重渐进）、epoch 软失效（标记代替硬清） | 数据说话再上 |

判据：§8 的 `cache_*` 指标里归队后的 miss 率与 DB QPS 尖峰。

## 6. 集群配置与端点

### 6.1 配置扩展（cpppools.json）

```json
{
  "server": { "port": 8080, "worker_threads": 6 },
  "cluster": {
    "node_id": "node-a",
    "epoch": 1,
    "nodes": [
      { "node_id": "node-a", "host": "10.0.0.1", "port": 8080 },
      { "node_id": "node-b", "host": "10.0.0.2", "port": 8080 }
    ]
  },
  "cache": {
    "enabled": true,
    "max_entries": 100000,
    "max_bytes": 268435456,
    "max_entry_bytes": 65536,
    "ttl_ms": 60000,
    "blacklist_ttl_ms": 60000,
    "tables": []
  },
  "datasources": [ "... 所有节点完全相同 ..." ]
}
```

- `cluster` 段缺省 = **单节点模式**：`is_owner` 恒真、无 epoch 门控，
  现有行为完全不变（保证期 1 可独立验证）。
- `node_id` 必须出现在 `nodes` 中（fail-fast）；`blacklist_ttl_ms ≥ ttl_ms`
  （不变量 I1，fail-fast）。
- `cache.tables` 为空 = 全部表可缓存；非空 = 白名单（供"有外部写入者的表"
  逐表关缓存，§1.2 的逃生舱）。
- 解析风格照抄既有 `server` 段：可选段 + 逐字段范围校验 + `return fail(...)`。

### 6.2 `GET /api/v1/cluster`（新端点）

```json
{
  "epoch": 1,
  "self": "node-a",
  "hash": { "algorithm": "murmur3_32", "seed": 0, "unsigned": true,
            "vnodes_per_node": 100, "attempt_base": 0 },
  "ttl": { "cache_ttl_ms": 60000, "blacklist_ttl_ms": 60000 },
  "nodes": [ { "node_id": "node-a", "host": "10.0.0.1", "port": 8080 } ],
  "datasource_digest": [ { "name": "main", "type": "sqlite", "digest": "<hex>" } ]
}
```

建环与一致性所需参数**全部自包含**（含两个 TTL，支撑 I1 的跨进程一致）。
单节点模式返回单节点列表（SDK 逻辑统一）。

### 6.3 数据源配置一致性校验（评审 S9）

§2 的"所有节点数据源配置完全相同"是被加粗的关键结构约束，却无强制手段：
一个节点的 `sqlite.path` 写错 ⇒ 它作为某些键的 owner 去读写**另一个库** ⇒
静默数据错乱。

**机制**：`/api/v1/cluster` 回传 `datasource_digest`（名称 + type +
目标标识的 hash，**不含任何凭据**）。SDK/运维在拉拓扑时比对全节点摘要，
不一致则告警（SDK 打日志 + 计数，不阻断）。

## 7. SDK（Python，第一版）

### 7.1 参数默认值表（规范性）

| 参数 | 默认 | 说明 |
|---|---|---|
| `connect_timeout` | 1s | |
| `read_timeout` | **3s** | 必须 > 服务端 `db_acquire_timeout`(100ms)，否则会把"服务端正常返回 503"误判为超时并拉黑健康节点（触发 §5.3 t2' 灰度故障） |
| `retry_max` | 3 | 仅对可重试操作（§5.5） |
| `backoff_base` | 100ms | 指数退避 |
| `backoff_jitter` | ±25% | **必须有抖动**：无抖动的同步退避会在恢复时造成归队风暴 |
| `attempt_max` | 5 | 环上绕行次数上限 |
| `blacklist_ttl` | 服务端下发（默认 60s） | 见 I1 |
| `topology_refresh` | 30s（lazy） | epoch 不匹配时立即刷新 |
| `follow_redirects` | true | 跟随 307（不计入 retry_max） |

### 7.2 行为规范

- **拓扑**：启动强制拉取（逐 seed 重试，全失败抛异常，无默认兜底）；
  运行期刷新失败 → **继续用旧环 + 打点**（不报错）；`epoch` 变化即重建环。
- **建环**：本地建环，参数取自 `/api/v1/cluster`；引用 §3.2 黄金向量做测试。
- **绕行**：超时/连接失败 → 拉黑 owner → `attempt+1` 查环（跳过黑名单节点）
  → 携带 `X-CppPools-Fallback: 1`。**全部节点在黑名单时**：清空黑名单重试
  一轮再抛（避免"全员拉黑后永久拒服务"）。
- **黑名单联动**：拓扑刷新后清理已下线节点的黑名单条目（否则长跑会积累
  无效条目 —— Dora 有对应的 cleanup 动作）。
- **线程安全**：环、黑名单、拓扑计时器为跨线程共享可变状态；环用
  "构建新环后原子替换引用"（读者无锁、永不阻塞）。
- **连接复用**：`requests.Session` per-node（keep-alive），否则每请求握手
  会吃掉缓存收益。
- **头**：`X-Client-Id`（环境变量兜底链）、`X-Request-Id`、`X-CppPools-Epoch`；
  黑名单过期回切时首个请求带 `X-CppPools-Rejoin: 1`（best-effort）。
- **错误分类**：400 不重试；409 交调用方；307 跟随；503/超时退避重试；
  自增 insert 不自动重试。

## 8. 可观测性与验收指标

### 8.1 指标

`cache_*` 指标族（Prometheus，维度 = **per-datasource**，沿用既有
`{pool="<数据源名>"}` 标签；**不打 node 标签** —— 节点身份由抓取端的
`instance`/`job` 提供，服务端自打会与之冲突）：

```
cpppools_cache_hits_total / cpppools_cache_misses_total
cpppools_cache_entries / cpppools_cache_bytes
cpppools_cache_evictions_total / cpppools_cache_invalidations_total
cpppools_cache_bypass_total{reason="not_owner|fallback|epoch_mismatch|real_key|too_large|not_cacheable"}
cpppools_cache_flush_total{reason="rejoin"}
cpppools_cache_singleflight_merged_total
cpppools_cache_backfill_dropped_total          # 世代号检查拦下的回填（§4.3.1）
cpppools_redirects_total                       # 307（"有多少流量打错节点"）
```

`bypass` 按 reason 细分而不合并：`not_owner`（服务端自判）与 `fallback`
（客户端申报）是不同信号，合并会掩盖"流量打错节点"这一运维关键。

请求链路：`request_id` 贯穿（响应头 `X-Request-Id` + 日志）。
`/api/v1/stats` 增加 cache 聚合字段 + `cluster_epoch` / `node_id`。
取数入口：registry 需新增 `cache_stats()`（依赖 §4.1.1 的 `Entry::cache`）。

### 8.2 验收指标（评审 W10）

期 0 采集基线（缓存未上线时的读 p50/p99、DB 读 QPS）；期 1 验收门槛：

| 指标 | 门槛 |
|---|---|
| 热点读命中率 | ≥ 80% |
| 读 p99 | 降 ≥ 30% |
| DB 读 QPS | 降 ≥ 50% |
| 写 p99 退化 | ≤ 10%（双删 + 双重校验的代价） |

达不到则重新评估 §4.1.2 的方案选择与 §4.6 的写放大。

### 8.3 运行时 kill-switch

`cache.enabled` 支持**运行时切换**（`POST /api/v1/cache/disable|enable`）：
生产上疑似脏读时第一动作应是"立即关缓存"而非重启（重启会丢现场 + 抖流量）。
关闭后**失效仍继续执行**（I0）；重新开启无需清空。

## 10. 扩展位（本版不实现）

- **Redis 共享缓存模式**：同一缓存抽象换后端；该模式下环退化为负载均衡。
- **缓存前置到池外（方案 A）**：命中不占连接槽；前置条件是把校验管道提升到
  数据源级（§4.1.2）。
- **后端回吐更新后整行**：`do_update` 返回更新后的行 ⇒ 装饰器可回填而非失效，
  消除 §4.6 的写放大（届时"失效而非更新"的论证需相应更新）。
- **负缓存**（缓存"不存在"）：需处理 insert 后的负条目失效。
- **热键账本预热**（§5.6 优先级 3）。
- **影子缓存**（借鉴 Dora `CacheManagerWithShadowCache`）：只存键不存值的
  过滤器，回答"若容量更大本可多命中多少"，为 `max_entries` 调参提供数据。
- **动态成员**（etcd/控制面）：静态配置证明语义后再谈。

## 12. 已确认的关键决策汇总

1. 缓存主线 = **节点本地缓存 + 哈希环**；Redis 是扩展位。
2. 路由键 = 缓存键 = **`(datasource, table, 唯一键列, 键值)` 4 元组**；
   多唯一键取 schema 列序第一个；结构化元组实现，哈希用长度前缀编码。
3. **`RowCache` 每数据源共享一个实例**（不是 per-connection），内部分片锁。
4. 写语义 = write-through + **双删失效**（前置+后置，删除而非更新）+
   **世代号 CAS 回填** + TTL 60s。
5. **I0：失效永不 bypass**；bypass 只关读命中与回填。
6. **I1：`blacklist_ttl ≥ cache_ttl`**（服务端下发 + fail-fast）⇒ 归队清缓存
   降级为 best-effort 优化，不引入归队检测机制。
7. 归属门控 = **服务端自判 `owner(key)==self`**；请求头只能让节点更保守
   （提示单调性）。
8. 非 owner + 未声明绕行 ⇒ **307 重定向**（不做代理转发：无出向 HTTP 客户端、
   不占 worker 线程、无级联故障）。
9. 拓扑变更用 **epoch 门控**：epoch 不匹配即 bypass 缓存 + 客户端立即刷新。
10. 环参数**自选、非 Dora 字节兼容**：murmur3_32 seed=0、**无符号**、
    100 vnodes、attempt 从 0、UTF-8、LE32、确定性 tie-break；黄金向量入 spec。
11. 一致性契约 = **稳态同键强一致**（稳态含"无客户端绕行"）；跨键/绕行期/
    epoch 未收敛/外部写入者 → 最终一致，旧读 ≤ TTL。
12. **只缓存 kOk 且非空的单行**；REAL 键列按**列类型**判定不缓存且不参与环路由。
13. 命中仍需借连接（方案 C 的已知限制）；方案 A 列为 v1.1，触发条件见 §4.1.2。
14. 容量**双阈值 + 单条上限**；`steady_clock`；快照时刻 = 发起 DB 读的时刻。
15. 外部写入者可见性列为**非目标**，逃生舱 = `cache.tables` 白名单。
